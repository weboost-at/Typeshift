# Working on this repository

Agentic is a .NET 10 library for code-defined agents and toolsets on Microsoft.Extensions.AI, plus the Roslyn
incremental generator that powers it. This file is the map: find your task below, read what it points at, and follow
the playbook. That is meant to be enough; if you had to dig for something, add it here or to a playbook.

## Start here

| Task | Read first | Playbook |
|---|---|---|

- **Why is the code like this?** `docs/contributing/decisions.md` (D1, D2, ...) records each non-obvious choice, the
  alternatives that lost, and where it lives. A comment `// D29: ...` in code points at one. Read the entry before
  you change such code; to change the decision, edit the entry in the same commit, or add a new one and mark the old
  "Withdrawn".
- **What is open?** `docs/contributing/status.md`: known gaps, next steps, and which test covers each behavior of the
  spec.
- **How do users see it?** The guide in `docs/guide/`, published at https://weboost-at.github.io/Agentic/.

## Traps

Each of these cost a debugging session once.

- The generator targets netstandard2.0 and Roslyn 4.14: no `Index`/`Range`, no list patterns, no newer Roslyn APIs.
- Generator models must stay equatable: no `ISymbol`, `SyntaxNode` or `Location` in them, or caching breaks.
- `UseToolset<T>(tools => tools.X())` does not bind inside the generator's own compilation, since the generator writes
  `X()`; the parser reads it from syntax (D29).
- Generated code compiles into the consumer and sees only public API; what only it calls is public and hidden from
  editors (D35).
- Generated `Settings` and `Overrides` serialize member by member through `StorableJson`; no `JsonSerializerContext`
  can see generated types (D27). Configurable members are limited to the types AGT014 lists.
- Every agent's settings type is named `Settings`: stores key data by `typeof(TData).FullName`, never `Name`.
- Toolsets, agents, runtimes and the store are singletons; each tool call gets a DI scope of its own (D11).
- The provider never receives `ChatOptions.ConversationId` (D18); only ids the store's `TId` parses are stored (D33).
- `AddAgentic()` works only as a direct call the generator intercepts (D1).
- Markdown between `<!-- snippet: x -->` and `<!-- endSnippet -->` is generated by `dotnet mdsnippets`; edit the
  sample code instead.
- `Agentic` is taken on nuget.org; the package ID is still to be chosen (D38).

## Build and test

```bash
dotnet tool restore
dotnet build -c Release -warnaserror
dotnet test -c Release --no-build
dotnet run --project samples/Agentic.Samples.Docs -c Release --no-build
dotnet slopwatch analyze --fail-on warning
dotnet mdsnippets && git diff --exit-code
dotnet publish samples/Agentic.Samples.Console -c Release -r linux-x64 -o artifacts/sample
```

- The build is warning-free with `TreatWarningsAsErrors`. The only suppressed warning is CS1591 in `tests/`.
- Generator snapshots live in `tests/Agentic.Generators.Tests/Snapshots`. A mismatch writes `.received.txt`; review
  it, then rerun with `ACCEPT_SNAPSHOTS=1` to accept.
- Run the whole suite three times before you call a change done. All green every time.
- Native AOT needs `clang` (or `-p:CppCompilerAndLinker=gcc`). CI publishes the sample with zero IL2xxx/IL3xxx
  warnings and runs it, then packs and runs `samples/Agentic.Samples.PackageConsumer` against the package.
- The docs site: `npm ci`, then `npm run docs:build` (fails on dead links) or `npm run docs:dev`.

| `Repository/DecisionCitationTests` (generator tests) | Every `// Dnn:` in code names a decision in force. |
| `Diagnostics/DiagnosticCatalogTests` (generator tests) | Every released diagnostic has a docs row, a docs section and a test. |

## Code style

The code must read as if the owner wrote it: terse, intention-revealing, comment-free by default.

- File-scoped namespaces. `record` for values, settings, stored documents and messages; classes where behavior lives.
- Seal generated classes, assertion classes and classes whose inheritance would be a bug; leave the rest open.
- Expression bodies for single-statement members. Guards are braceless one-liners stacked at the top.
- Switch expressions over `if`/`else` chains; `is null` / `is { } x`, never `== null`.
- Collection expressions, `var`, named arguments where positional ones blur.
- Extension members use C# 14 `extension(...)` blocks, never `this` parameters. The one exception is the generated
  interceptor, whose signature must mirror the intercepted call.
- Events are `On<EventName>`. A method that computes and returns something is `Get...`. A token is `ct` when the
  signature puts one parameter per line.
- Fluent chains one call per line; blank lines around multi-line statements; a statement-level object initializer
  is multi-line; no trailing commas.
- Comments only where they earn their place: one line, saying why, never what.
- XML docs on every public member and none on private or internal ones: a `<summary>` of what it is or does, plus
  every `<typeparam>`, `<param>`, `<returns>` and the `<exception>`s a caller can act on, in plain sentences a reader
  takes in at a glance. Anything that needs more than a few sentences goes to the docs site.
- No guard for a state that cannot occur, no duplicated helper, no dead code, no TODOs (open items go to
  `docs/contributing/status.md`).
- Never read the clock: inject `TimeProvider` (`GetTimestamp`, `GetElapsedTime`, `Task.Delay(span, time)`,
  `new CancellationTokenSource(span, time)`).
- No reflection over user types on generated paths, no static mutable state, JSON through `JsonTypeInfo` only.

## Generator rules

- Discovery is attribute-free: a class with a base list that is not abstract, checked semantically.
- Parser and emitter stay apart. Models hold only strings, bools and `EquatableArray<T>`; locations are
  `LocationInfo`. An agent model never holds another class's syntax: agents are resolved against toolsets in a
  combined step.
- Cross-assembly data travels only through the stamps (assembly and class attributes).
- Name the pipeline steps; an unrelated edit must leave every output cached.
- Generated code is `global::`-qualified, starts with `// <auto-generated/>` and `#nullable enable`, never hides an
  inherited member, and compiles warning-free in a consumer with documentation on.
- A new diagnostic gets a descriptor, a release row, a docs row and section, and its own test; the
  `add-diagnostic` playbook lists the steps.

## Tests

The rules come from the owner's skills; the convention tests in `tests/Agentic.Tests/Testing/Conventions` enforce
them for every test project, and their exemption list stays empty.

- One test class per subject, one business rule per test, named `Given_<state>_<outcome>` (or `<outcome>` for the
  base case); the declaration fits 120 columns.
- Only `// Arrange`, `// Act`, `// Assert` and `// Act & Assert` comments in test bodies.
- One assertion per statement: no `.And`, `.Which` or `.Subject`. A recurring check becomes an assertions class
  exposed as `.Assert` through an extension block, in `Testing/Assertions`.
- Test data comes from the catalog (`Data`, seeded per test). No `new Faker(` outside it.
- Time moves only through `FakeTimeProvider.Advance`. No `Task.Delay`, `Thread.Sleep` or real clocks; order
  concurrent work with `TaskCompletionSource` gates.
- Bases, fakes, data and helpers go in `Testing/` or `<Area>/Support/`; other folders hold test classes only.
- Never wrap a bug in a green test, never weaken an assertion, never skip a test.

## Commits

- Subject: `<Past-tense verb> <file or feature>, <what changed>`, at most 72 characters, no type prefix, no
  semicolon, no trailing period. A body only when the reason is not obvious, wrapped at 72.
- One logical change per commit that builds and passes; a type and its tests go together.
- Stage by pathspec, never `git add -A`. Never commit `.context/`.
- Check every message before committing with the owner's `git-commit` skill when it is installed (it is not part of
  this repository); otherwise check the rules above by hand.
