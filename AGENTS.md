# Working on this repository

Typeshift is a .NET 11 library for code-defined agents and toolsets on Microsoft.Extensions.AI, plus the Roslyn
incremental generator that powers it. This file is the map: find your task below, read what it points at, and follow
the playbook. That is meant to be enough; if you had to dig for something, add it here or to a playbook.

## Traps

Each of these cost a debugging session once.

- The generator targets netstandard2.0 on Roslyn 5 (D8): no `Index`/`Range`, no list patterns.
- Generator models must stay equatable: no `ISymbol`, `SyntaxNode` or `Location` in them, or caching breaks.
- The generator never reports; the analyzer does, with the same parsers (D2). A shape the parser rejects must be
  skipped by the generator, or generated code fails with a compiler error the user cannot read.
- An exception in the generator drops every generated file of the project (CS8785), and code being typed is full of
  symbols that invite one: `UseToolset<>()` names an error type, with no containing assembly and an empty name.
- The analyzer sees the generated code too: a check for user members excludes generated trees (`Names.IsGenerated`).
- `UseToolset<T>().Include(t => t.X)` cannot bind inside the generator's own compilation, since the generator writes
  `t.X`; the parser reads picks from syntax and the analyzer reports every other shape (D4).
- mdsnippets skips any file named `agents.md`, `claude.md`, `gemini.md` or `copilot-instructions.md`, whatever its
  folder and case, so no docs page may have such a name. `lint.mjs` fails on one, and on a `snippet:` line the tool
  left as it was.
- No builder inside a lambda: every declaration is one chain (D17). At runtime the chains declare nothing (D4).
- Generated code compiles into the consumer and sees only public API; what only it calls is public and hidden from
  editors (D10).
- Markdown between `<!-- snippet: x -->` and `<!-- endSnippet -->` is generated by mdsnippets; edit the sample code
  instead.
- Run mdsnippets as `npm run docs:snippets`, never as `dotnet mdsnippets`. The tool rewrites every Markdown file at
  once, README.md included, and once replaced about 40 uncommitted README lines without a word. The script prints
  the uncommitted lines a run replaced and keeps the file as it was under `.context/mdsnippets-backup/`.
- A test that resolves a scoped service needs a scope: `HostTestBase` builds with `ValidateScopes` and offers `Scope`.

## Build and test

```bash
dotnet tool restore
dotnet build Typeshift.slnx -c Release -warnaserror
dotnet test --solution Typeshift.slnx -c Release --no-build
dotnet run --project samples/Typeshift.Samples.Docs -c Release --no-build
dotnet publish samples/Typeshift.Samples.Console -c Release -r linux-x64 -o artifacts/sample
./artifacts/sample/Typeshift.Samples.Console
dotnet slopwatch analyze --fail-on warning
npm run docs:snippets:check
```

- Cloud sessions run `.claude/hooks/session-start.sh`: the skills pinned to reviewed commits (the owner's, ponytail's
  and `humanizer`), the .NET SDK `global.json` asks for (from dot.net; a limited network has to allow dot.net and
  builds.dotnet.microsoft.com), the tools and the packages. A step that fails is named in the hook's last line and
  does not stop the others. An environment's own setup script has to install the same SDK.
- `global.json` pins the .NET 11 SDK, and every project targets `net11.0` (D61).
- The build is warning-free with `TreatWarningsAsErrors`. CS1591 is switched off in `tests/.editorconfig` and
  `demos/.editorconfig`, and by the package for a consumer that never chose XML docs (D68). Three test files disable
  TSH024, TSH028 and TSH030 by pragma, each with its reason beside it.
- Generator snapshots live in `tests/Typeshift.Generators.Tests/Snapshots`. A mismatch writes `.received.txt`; review
  it, then rerun with `ACCEPT_SNAPSHOTS=1` to accept. An accept run rewrites every snapshot, so read
  `git diff tests/Typeshift.Generators.Tests/Snapshots` before you commit. A snapshot holds the generated files its
  test names in `Snapshot.Verify`, so that one test pins a file and a change of it is one snapshot's diff.
- The public API is a snapshot in the same folder: `PublicApi.verified.txt` holds every public type and member, one
  line each. A change of public API fails `PublicApiSurfaceTests` until you read the difference to
  `PublicApi.received.txt` and accept it with
  `ACCEPT_SNAPSHOTS=1 dotnet test --project tests/Typeshift.Generators.Tests -c Release --no-build`. Commit the
  snapshot with the change, so a reviewer reads the API change as its diff. `GeneratedContract.verified.txt` holds
  what generated code binds to, and is accepted only after `ReferenceReader.StampVersion` was raised (D7).
- Run the whole suite three times before you call a change done. All green every time.
- The docs site: `npm ci`, then `npm run docs:check` (the snippets against their sources, markdownlint, the docs
  rules, a build that fails on dead links) or `npm run docs:dev`.
- The demos in `demos/` stay outside the solution and CI, by the owner's choice. Until a scheduled workflow builds
  them, build them at the start of each session: `dotnet build demos/Typeshift.Demos.slnx -c Release`. If the build
  fails, give the owner a short note and go on with your task. A change to public API builds them again before you
  push; when it breaks one, fix it in the same PR, or say so under a **Demos** heading in the PR's description.

## Docs

The guide is for library users, `docs/contributing/` for this repository. `docs/contributing/writing.md` holds the
style; the essentials:

- Every page: `title` and `description` frontmatter, an H1 equal to the title, a lead of two or three sentences that
  answers first, no summary box, one idea per section, `## Related` last.
- Present tense, "you" for the reader and "your app" for their application; "the host" is only `AgentHost<TAgent>`.
  Explain rather than compress: spell out the step between two facts, in sentences of varied length that read like a
  person wrote them. Say why, once. No filler, no em dashes, no trailing "say" for examples: "for example".
- Keep it compact: a new topic is a section of an existing page before it is a page of its own. Short paragraphs;
  facts about a snippet as a list.
- Pitch lines (README, home page, leads) name what the reader does, such as "Create an agent", in plain words rather
  than slogans. They never lead with what the generator emits and never say "plain C#". Getting started stays at
  about four steps.
- C# only from `samples/Typeshift.Samples.Docs` through mdsnippets. Callouts carry meaning and a title. Mermaid for
  flows, at most about ten nodes.
- One fact, one page: change the canonical page below and link to it elsewhere. A snippet may repeat; its
  explanation may not.

## Code style

The code must read as if the owner wrote it: terse, intention-revealing, comment-free by default.

- File-scoped namespaces. `record` for values, settings, stored documents and messages; classes where behavior lives.
- Seal generated classes, assertion classes and classes whose inheritance would be a bug; leave the rest open.
- Expression bodies for single-statement members. Guards are braceless one-liners stacked at the top.
- Switch expressions over `if`/`else` chains; `is null` / `is { } x`, never `== null`.
- Collection expressions, `var`, named arguments where positional ones blur.
- Extension members use C# 14 `extension(...)` blocks, never `this` parameters. The one exception is the generated
  interceptor, whose signature must mirror the intercepted call.
- Events are `On<EventName>`. A method that computes and returns something is `Get...`. A token is `ct` when the
  signature puts one parameter per line.
- Fluent chains one call per line; blank lines around multi-line statements; a statement-level object initializer
  is multi-line; no trailing commas.
- Comments only where they earn their place: one line, saying why, never what.
- XML docs on every public member and none on private or internal ones: a `<summary>` of what it is or does, plus
  every `<typeparam>`, `<param>`, `<returns>` and the `<exception>`s a caller can act on, in plain sentences a reader
  takes in at a glance. Anything that needs more than a few sentences goes to the docs site.
- No guard for a state that cannot occur, no duplicated helper, no dead code, no TODOs (open items go to
  `docs/contributing/status.md`).
- Never read the clock: inject `TimeProvider` (`GetTimestamp`, `GetElapsedTime`, `Task.Delay(span, time)`,
  `new CancellationTokenSource(span, time)`). The build reports a real clock as RS0030, with what to write instead;
  the few intended uses carry `#pragma warning disable RS0030` and their reason. Only an app names
  `TimeProvider.System`, which here means a sample.
- `shortcut: <the limit>, <when to upgrade>` comments mark a known limit; list them with `ponytail-debt` and carry
  them into `status.md` by hand.
- No reflection over user types on generated paths, no static mutable state, JSON through `JsonTypeInfo` only.

## Generator rules

- Discovery is attribute-free: a non-abstract class whose base list names `Toolset` (D3), checked semantically.
- Parser and emitter stay apart. Models hold only strings, bools, enums and `EquatableArray<T>`, never locations.
- The analyzer reports every diagnostic, with the parsers the generator uses (D2).
- Cross-assembly data travels only through the stamps (assembly and class attributes).
- Name the pipeline steps; an unrelated edit must leave every output cached.
- The output is the same on every build machine: compare with `StringComparison.Ordinal`, format with
  `CultureInfo.InvariantCulture`. The CA rules of the guard table miss a number inside an interpolated string.
- Generated code is `global::`-qualified, starts with the header of `SourceWriter`, never hides an inherited member,
  and compiles warning-free in a consumer with documentation on. The header is `// <auto-generated/>`,
  `#nullable enable` and `#pragma warning disable CS0612, CS0618`, plus the ids of the `[Experimental]` symbols the
  file names. A generated file never carries a bare `#pragma warning disable`, which would hide what the guard tests
  look for.
- A generated type, and a member generated into a class of the user's, carries `Names.Generated`: `[GeneratedCode]`
  and `[ExcludeFromCodeCoverage]`. The user's partial class never does, since analyzers skip what the attribute
  marks.
- A new diagnostic gets a descriptor, a release row, a docs row and section, and tests of its own, the first of
  them with its whole message; the `add-diagnostic` playbook lists the steps. Its ID is the number after the highest
  ever used, the retired ones in `docs/guide/diagnostics.md` included, and a gap is never filled (D49).
- Every shape of user code a change touches gets one field in a catalog of
  `tests/Typeshift.Generators.Tests/Diagnostics/Support`, which a theory runs: `ShapeSources` when the parser accepts
  it, `DiagnosticSources` when it rejects it, `HalfTypedSources` when it made the generator or the analyzer throw.

## Tests

The rules come from the owner's skills; the convention tests in `tests/Typeshift.Tests/Testing/Conventions` enforce
them for every test project, without exemptions. A failure reads `<file>:<line>: <what>: <what to do>`.

- One test class per subject, one business rule per test, named `Given_<state>_<outcome>` (or `<outcome>` for the
  base case); the declaration fits 120 columns and reads `public void`, `public async Task` or the like, never
  `static`.
- A test class has a file named after it, in the folder its namespace names. `UnitTestBase`, `HostTestBase` and the
  areas' bases such as `AgentTestBase` hold `Ct`, `Time` and `Data`; `GeneratorTestBase` holds `Ct`.
- Only `// Arrange`, `// Act`, `// Assert` and `// Act & Assert` comments in test bodies: none behind a statement,
  none between `/*` and `*/`. A `#pragma` keeps its reason beside it. No `#region` in a test file.
- Every test asserts, with `.Should()`, an `.Assert` helper or `Snapshot.Verify`.
- One assertion per statement: no `.And`, `.Which` or `.Subject`. A recurring check becomes an assertions class
  exposed as `.Assert` through an extension block, in `Testing/Assertions`.
- Test data comes from the catalog (`Data`, seeded per test). No `new Faker` outside it.
- Time moves only through `FakeTimeProvider.Advance`. No `Task.Delay`, `Thread.Sleep` or real clocks; order
  concurrent work with `TaskCompletionSource` gates.
- Take `Ct` from the test base and await every gate with it (`.WaitAsync(Ct)`), never with a time of its own
  (`.WaitAsync(TimeSpan.FromSeconds(5))`) and never with `TestContext.Current.CancellationToken`, although the hint
  of xUnit1051 names it. `Ct` cancels after 20 seconds of real time, the one real clock the tests allow, so a gate
  nothing opens fails its test instead of hanging the suite. When a run hangs all the same, start the test
  project's executable in `bin/Release/net11.0`: it names every test that runs for 30 seconds or longer, which
  `dotnet test` does not show.
- Bases, fakes, data and helpers go in `Testing/` or `<Area>/Support/`; other folders hold test classes only.
- Never wrap a bug in a green test, never weaken an assertion, never skip a test: no `Skip`, no `Explicit`, no
  `Assert.Skip`.
- Review-only, since no pattern sees them: one rule per test, an assertion that is the one the name promises, and
  an assertion that was weakened.

## Commits

- Subject: `<Past-tense verb> <file or feature>, <what changed>`, at most 72 characters, no type prefix, no
  semicolon, no trailing period. A body only when the reason is not obvious, wrapped at 72.
- One logical change per commit that builds and passes; a type and its tests go together.
- Stage by pathspec, never `git add -A`. Never commit `.context/`.
- Check every message before committing with the owner's `git-commit` skill when it is installed (it is not part of
  this repository); otherwise check the rules above by hand.
